# Аналитика: Яндекс Метрика № 105193463 и конверсии

**Дата:** 9 октября 2026

---

## 1. Счётчик и способ интеграции

- Счётчик **существующий, номер 105193463** — новый не создавался.
- Подключение: `src/components/YandexMetrika.tsx` → официальный `tag.js` через `next/script` (`afterInteractive`) в root layout. ID вынесен в константу `YM_COUNTER_ID` (`src/lib/analytics.ts`).
- **Согласие на cookie:** счётчик монтируется только после принятия согласия (существующее решение, `useCookieConsent` + localStorage `cookieConsent`). Данные до согласия не собираются — юридически осторожно, но недоучитывает визиты. Альтернатива (загружать счётчик сразу, Вебвизор — только после согласия) требует решения владельца.
- Инициализация: `webvisor: true, clickmap: true, accurateTrackBounce: true, trackLinks: true` — Вебвизор, карта кликов/ссылок и точный показатель отказов включены. После входа в интерфейс Метрики проверить, что данные пункты активны в настройках счётчика (галочки в UI могут переопределять init-флаги).
- CSP пропускает mc.yandex.ru (script/img/connect/wss) — проверено заголовками на prod-сборке.
- `<noscript>`-пиксель сохранён.

## 2. SPA-отслеживание (главное исправление)

Раньше hit отправлялся только при загрузке HTML — все переходы `next/link` были невидимы для
Метрики (вероятная причина «глубины 1,15»). Теперь компонент следит за `usePathname()` и при
каждом клиентском переходе отправляет `ym(105193463, 'hit', <url>, { referer: <предыдущий путь> })`.
Первый hit по-прежнему отправляет сам tag.js при инициализации — дублей нет (проверено логикой
`lastTrackedPath`). UTM-метки входа фиксируются tag.js автоматически; back/forward и прямое
открытие URL покрываются штатно.

## 3. Реализованные события (reachGoal)

Обёртка `ymReachGoal` (`src/lib/analytics.ts`): union-тип целей, проверка `window.ym`,
заглушка-очередь до загрузки tag.js, молчаливая обработка ошибок, без персональных данных.

| Цель | Где срабатывает | Параметры |
|------|-----------------|-----------|
| `booking_click` | Все кнопки «Записаться»: hero главной, секция записи, страницы услуг, плавающая кнопка, меню (бургер), футер, промо-страница (5 CTA), промо-попап | `service` (slug услуги / `home` / `promo`), `placement` (`hero`, `singup_section`, `service_page`, `floating`, `header`, `footer`, `promo`, `promo_popup`) |
| `phone_click` | Телефоны в меню и футере (текст и иконка) | `placement` (`header`, `footer`) |
| `messenger_click` | Кнопки «Max» (плавающая, меню, футер) | `channel: 'max'`, `service` (для плавающей) |
| `reviews_click` | «Перейти к отзывам» (Яндекс Карты) на страницах услуг | — |
| `service_view` | Просмотр страницы услуги (в т.ч. клиентские переходы) | `service` (slug) |

## 4. Воронка и её границы

```
Визит ──► service_view (просмотр услуги) ──► booking_click (клик «Записаться»)
                                              └─► переход в YCLIENTS (внешняя форма)
```

- `booking_form_open` / `booking_form_submit` на сайте реализовать нельзя: **форма записи — внешний
  виджет YCLIENTS** (n782275.yclients.com), недоступный для нашего JS. Подтверждённые записи можно
  брать только из API/отчётов YCLIENTS и сопоставлять с Метрикой по датам (вручную) или через
  офлайн-конверсии.
- Клик по телефону **не считается** записью — только обращением.
- Клик по Яндекс-карте не отслеживается технически (клик внутри кросс-доменного iframe не
  всплывает в документ) — честно фиксируем как ограничение.

## 5. Цели, которые нужно создать вручную в Метрике

Интерфейс: Метрика → Настройки → Цели → Добавить (тип «JavaScript-событие», идентификатор = имя
цели). `reachGoal` не создаёт цели автоматически:

1. `booking_click` — ретаргетинговая, считается главной конверсией.
2. `phone_click`
3. `messenger_click`
4. `reviews_click`
5. `service_view` (для анализа интереса к услугам; в конверсии не считать)
6. (Опционально) составная цель-воронка `Визит → service_view → booking_click`.

## 6. Рекомендуемые настройки счётчика (в интерфейсе, при наличии доступа)

- **Фильтры:** добавить свой IP-адрес (и IP салона) в «не учитывать мои визиты» — иначе тестовые
  визиты команды портят данные.
- **Часовой пояс:** проверить «(GMT+4) Саратов/Волгоград/Самара…».
- **Вебвизор, карта кликов, карта ссылок:** убедиться, что включены (в init уже включены).
- **Аналитика форм** бесполезна для внешней формы YCLIENTS.
- **Уведомления/отчёты:** включить еженедельный отчёт на почту владельца.
- **Параметры посетителей** не передаются (нет авторизованной зоны) — корректно.

## 7. Проверка после деплоя (чек-лист)

1. Открыть сайт → принять cookie → в Метрике «Отчёт в реальном времени» появляется визит.
2. Перейти из меню на «Биозавивку» → в реальном времени просмотр страницы `/bioavailability` (не только `/`) + цель `service_view`.
3. Кликнуть «Записаться» → цель `booking_click` с параметром service/placement.
4. Позвонить по tel-ссылке с телефона → `phone_click`.
5. Вебвизор: запись посещения воспроизводится, движения мыши видны.
6. Через 2–4 недели: сравнить глубину просмотра до/после — теперь она отражает реальность.

## 8. Известные ограничения

- До принятия cookie-согласия аналитики нет вообще (см. п.1) — при необходимости сменить модель.
- `booking_form_submit` и подтверждённые записи — вне сайта (YCLIENTS).
- Параметр `placement` у `booking_click` и `channel` у `messenger_click` видны в отчёте по целям
  только после создания цели и в «Параметрах визитов» при просмотре по сегментам.
- WhatsApp/VK-ссылки есть в content.json, но в интерфейсе не используются — события не вводились.
